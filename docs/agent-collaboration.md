# 多 Agent 协作说明

## 调度原则

用户授权主 agent 自行按需调度。先判断任务能否独立交付；没有实质并行收益或任务很小时，直接处理，不为使用 agent 而拆分。

- **Luna Max**：查找与整理资料、文档校对、明确步骤的批处理/测试、日志检查、进程等待、结果汇总。
- **Sol（最高 High）**：复杂跨模块实现、接口设计、并发与取消竞态、疑难排障、需要综合判断的审查。
- 禁止 Astra；不使用 Sol 的 xhigh/max/ultra。简单任务不因等待时间长就交给 Sol。
- 如果受派 agent 无法解决，先带证据汇报，再由主 agent 判断是否交给 Sol；不得自行越级或递归开团队。
- 模型不可用时不静默改用更贵模型。规则描述的是本项目可调度子 agent 上限，不代表可以改动用户当前会话模型。

## 分工契约

派工至少包含：目标、输入/版本、允许修改的文件、禁止碰的资产、共享资源约束、预期输出及验证方法。短上下文足够时不传完整聊天历史。

同一时间一个文件只由一个 agent 写；接口先由主 agent 定义，依赖接口的工作等契约明确后再并行。GPU 推理/训练、模型换权重、共享配置修改串行安排。

子 agent 不自行 commit/push、重置文件、安装无关依赖或改变任务范围。主 agent 负责检查差异、解决冲突、串接接口和执行最终验收。

## 长任务与通知

优先使用任务结束、子进程退出或日志完成信号。必须轮询时默认分钟级或退避；根据明确截止时间安排一次检查，避免多个 agent 同时监控同一进程。

运行时及时处理异常，但正常进度无需逐轮消息。子 agent 只在完成、失败、重要风险变化或缺少必要信息时通知主 agent；主 agent 汇总后再向用户报告。

等待工具受单次时长限制时可续等，但不要每次醒来都重新扫描日志或向用户播报。监控工作交给 Luna Max，主 agent 不重复做同样检查。

## 回传格式

每次交付用简短条目说明：

1. 结果与实际修改文件。
2. 执行的检查及结果，附必要日志/产物路径。
3. 未验证项、失败原因或需要主 agent 决策的点。

完成以产物和证据为准。相同问题避免多 agent 重复调研，复用已有 [开源调研](./desktop-voice/research.md) 和本地检查结果；新证据再补充。
